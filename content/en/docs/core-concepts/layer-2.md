title: 'Layer 2: Agent Definitions'
description: Roles, access boundaries, and retry policy for every agent in CAF.
---

Layer 2 defines who does what. Every role in the pipeline has its own definition
file in `.claude/agents/` — generated by `caf-init scaffold agents`, already informed
by context from [Layer 1: Project Knowledge Base](/docs/core-concepts/layer-1).

## The roles

CAF Initiator offers a roster to pick from: Planner, Architect, Frontend and Backend
(per assigned app), extra per-app implementation agents, QA, Reviewer,
Documentation, Auditor, PM and UX Designer. CAF recommends starting with Planner
plus one implementation agent.

CAF Orchestrator's pipeline runs a subset of these in sequence, called by filename:

| File | Role | Tools |
|---|---|---|
| `caf-planner.md` | Drafts `requirements.md` and `tasks.md` from the ticket | `Read`, `Write` — artifacts only, no code |
| `caf-frontend.md` / `caf-backend.md` | Writes code per the plan, inside its own scope | `Read`, `Write`, `Edit`, `Bash` |
| `caf-qa.md` | Checks the work against the acceptance criteria, runs tests/build | `Read`, `Bash`, `Write` for `qa-report.md` — does not change code |
| `caf-reviewer.md` | Reviews the diff and writes a verdict | `Read`, `Bash`, `Write` for `review-notes.md` |
| `caf-documentation.md` | Updates docs affected by the change | `Read`, `Write`, `Edit` |

`caf-reviewer.md` does **not** replace a human. Its verdict makes it easier for a
human to decide — the merge decision always stays with a human.

In a single-package repo, `scaffold agents` offers one implementation agent,
`caf-implementer.md`, instead of the frontend/backend split. The Orchestrator does
not route that filename; pass `--role frontend` or `--role backend` to generate the
same agent as `caf-frontend.md` / `caf-backend.md`.

## What's inside a definition file

- **Role** and **Scope** — the boundaries of that role's responsibility
- **Allowed Tools** — which tools the agent may use (see the table above)
- **Input** / **Output** — the artifacts it reads and must write (see
  [Layer 3: Artifact Handoff](/docs/core-concepts/layer-3))
- **Working Pattern (PIV)** and **Verify Checklist**
- **Retry Logic** and, for QA, Reviewer and Auditor, **Report Format** — the exact
  status lines CAF Orchestrator parses
- **Skills** — optional pointers to the CAF skills (below)
- **Constraints**

## Skills

`caf-init scaffold skills` writes five universal skills into
`.claude/skills/<name>/SKILL.md`: `caf-verify`, `caf-scope-discipline`,
`caf-no-guess`, `caf-escalate` and `caf-piv`. An agent reaches them through `Read`
pointers in its `## Skills` section; a manual Claude Code session picks them up by
their description. Skills are guidance — enforcement stays with the Verify, QA and
Reviewer stages. See [CAF Initiator](/docs/caf-initiator#caf-init-scaffold-skills).

## Customization

These files aren't locked-down configuration. `Role`, `Scope`, `Verify Checklist`,
`Constraints` and `Skills` hold per-project data and are yours to edit — for
example, adding a rule to `caf-backend.md` like "always write a test for every new
function."

The other sections are **tracked**: `caf-init curate` compares them with the current
template so a template fix can reach agents generated earlier. A tracked section you
edited by hand is reported, never overwritten. If you run through CAF Orchestrator,
leave `Retry Logic` and `Report Format` as generated — the Orchestrator parses their
status lines word for word.

## Relationship to other layers

Layer 2 consumes context from **Layer 1** and determines the artifact format that
gets written to [Layer 3: Artifact Handoff](/docs/core-concepts/layer-3) at the end
of every phase.
